# Контракты служебных страниц и смысловых визуалов

## Источники страниц

- `site-content.json`: главная и семь продуктов ПО.
- `secondary-content.json`: шесть аудиторий, их индекс, компания, поддержка, контакты, подключение.
- `utility-content.json`: индекс ПО, провайдеры, загрузки, оборудование и правила системы.
- `equipment-content.json`: карточки двух терминалов, характеристики и строки каталога комплектующих.

`source_urls`, `visual_description`, `motion`, `collection.display` и редакторские заметки служат разработчику. Не вставлять их в текст сайта. Поля `title`, `lead`, `body`/`paragraphs`, `bullets`, подписи действий и предусмотренные сообщения являются публичным текстом. Если `value` равно `null`, это отсутствие значения, а не «0» или «неизвестно» на экране.

## HTML как визуальное подтверждение

Скриншот кассира не объясняет отчётность провайдера или управление сетью. Поэтому для ряда секций подготовлены предметные HTML-композиции с явными данными. Они не имитируют личный кабинет.

### `html-feature-list`

Данные: `visual_fields: [{label: string, value: null}]`. Вывести список конкретных функций, перечисленных в секции. Например, «Комиссии и наценки», «Инкассации», «Финансовые отчёты». Представление: одна или две колонки, тонкие горизонтальные разделители, маркер 4 px. Заголовок относится ко всему перечню; у элементов нет крупных подложек, иллюстраций и выдуманных чисел. Для `null` показывается только `label`.

Строка 44–56 px, текст 18 px desktop / 16 px mobile, цвет #111315. На ширинах до 767 px всегда одна колонка. Если смысл уже полностью выражен абзацем, список может стоять справа как его визуальный разбор, без повторного декоративного заголовка. Значения и лейблы нельзя дополнять генерацией.

### `html-process`

Данные:

```json
{
  "visual_nodes": [{"id": "n1", "label": "…"}, {"id": "n2", "label": "…"}],
  "visual_edges": [{"from": "n1", "to": "n2", "label": "…"}]
}
```

Многоточия здесь описывают тип полей; реальные подписи уже заданы в `secondary-content.json`. Ссылки `from/to` обязаны разрешаться в `visual_nodes`. Порядок чтения берётся из массива. На desktop узлы идут горизонтально, если их не больше трёх; более длинные процессы переносятся в две строки или вертикально. На mobile всегда вертикальный список с подписанными связями. Если граф имеет обратную связь, показывать отдельную подписанную линию, не подразумевать её.

Узел: непрозрачное светлое поле, рамка 1 px, радиус 4–8 px, отступ 24 px. Подпись 18 px medium. Стрелка 1.5–2 px, синий #0066B3. Анимация `process-step` только выделяет выбранный шаг; надписи видны сразу. Не делать поток «пакетов» и счетчики успешных операций.

### Отчётность

`html-report-fields` использует `visual_fields` и готовую `report-flow.svg`: «Платежи за период → Реестр → Отчёт». Не подменять её скриншотом РМА. Схема описывает обработку данных; строка с фиктивным платежом, банковским счётом или оборотом не нужна.

### Текст как предмет

`text-only` применяется к истории, именам, должностям и контактным состояниям, где нет подходящего изображения. Дата или имя становятся основным типографическим элементом, рядом находится исходный факт. Это намеренная композиция информационной страницы. Пустой слот под фотографию и случайная иллюстрация не выводятся.

## Индексы и каталог

`software-catalog` собирает семь записей из готовых страниц ПО. Первая запись терминального ПО широкая, две РМА сопоставляются, XML отображается собственной схемой. Название и ссылка берутся из страницы продукта, вводный текст из `sections[0].paragraphs`.

`provider-catalog` использует `providers-source.json` и логотипы из manifest по `logo_url`. Один и тот же файл логотипа может относиться к нескольким строкам услуг, поэтому число файлов не равно числу провайдерных записей. Сортировка по имени внутри категории, поиск без учёта регистра, отступов по краям запроса и различия ё/е. Поиск относится к названию, фильтр к `category_id`. Значение count вычисляется после обоих фильтров. 600 записей достаточно для локального поиска; API изобретать не требуется. При пагинации по 30 строк сбрасывать номер страницы на 1 при изменении поиска.

`equipment-catalog` использует только реальные карточки и строки `equipment-content.json`. Подписи с б/у сохраняются. Пользователь видит модель и параметры, а не старые проценты экономии. На главной при 360–767 px две модели можно сопоставить рядом; на более узких экранах и в подробном каталоге использовать вертикальные записи.

## Страница правил

Маршрут `/system-rules/` полностью описан в `utility-content.json`. H1 «Правила системы SkySend». Вводный текст «Откройте документ с правилами системы SkySend». Действие «Открыть PDF» ведёт на фактическую ссылку выбранного документа из `download-catalog.json`. Второе действие «Все документы системы» ведёт в соответствующую группу загрузок. Документ не переписывается и не обозначается как актуальная юридическая редакция только на основании HTTP 200. Не добавлять придуманную политику обработки данных.

## Приоритет анимаций

Во вторичных страницах числовые параметры задаёт `motion_alias` → `motion-spec.json.contentAliases`. `motion_intent` объясняет смысл. Первый экран всегда статичен независимо от анимации остальных секций. Основной HTML остаётся видимым без JavaScript.
